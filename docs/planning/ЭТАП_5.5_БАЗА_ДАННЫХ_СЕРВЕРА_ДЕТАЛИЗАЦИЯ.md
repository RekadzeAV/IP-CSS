## 📊 Компоненты этапа

### 5.5.1 Хранилище данных ✅ (100%)

#### Описание
Реализована система хранения данных с поддержкой PostgreSQL и SQLite. Используется SQLDelight для type-safe SQL запросов и управления схемой БД.

#### Технологии
- **SQLDelight** - генерация type-safe SQL кода
- **PostgreSQL** - основная БД для production (версия 9.5+)
- **SQLite** - для локальной разработки и desktop приложений
- **JDBC Driver** - для подключения к PostgreSQL

#### Структура базы данных

**Таблицы:**
1. **camera** - информация о камерах
   - `id`, `name`, `url`, `status`, `created_at`, `updated_at`
   - Индексы: `status`, `created_at`

2. **recording** - записи с камер
   - `id`, `camera_id`, `file_path`, `start_time`, `end_time`, `duration`, `file_size`, `status`, `created_at`
   - Индексы: `camera_id`, `start_time`, `status`, `created_at`

3. **event** - события с камер
   - `id`, `camera_id`, `type`, `severity`, `message`, `timestamp`, `acknowledged`, `acknowledged_at`, `acknowledged_by`, `metadata`
   - Индексы: `camera_id`, `type`, `severity`, `timestamp`, `acknowledged`

4. **user** - пользователи системы
   - `id`, `username`, `password_hash`, `role`, `is_active`, `created_at`, `updated_at`
   - Индексы: `username`, `role`, `is_active`

5. **setting** - настройки системы
   - `id`, `category`, `key`, `value`, `type`, `description`, `created_at`, `updated_at`
   - Индексы: `category`, `key`, `category+key` (composite)

6. **notification** - уведомления
   - `id`, `type`, `priority`, `title`, `message`, `read`, `read_at`, `timestamp`, `camera_id`, `event_id`
   - Индексы: `type`, `priority`, `read`, `timestamp`, `camera_id`, `event_id`

7. **schema_version** - версионирование схемы БД
   - `version`, `applied_at`, `description`
   - Индекс: `version`

#### Файлы реализации
- `shared/src/commonMain/sqldelight/com/company/ipcamera/shared/database/CameraDatabase.sq` - схема БД
- `shared/src/commonMain/kotlin/com/company/ipcamera/shared/data/local/DatabaseFactory.kt` - фабрика БД
- `shared/src/desktopMain/kotlin/com/company/ipcamera/shared/data/local/DatabaseFactory.desktop.kt` - desktop реализация

#### SQL Совместимость
Все SQL запросы используют синтаксис, совместимый с PostgreSQL и SQLite:
- `ON CONFLICT ... DO UPDATE` вместо `INSERT OR REPLACE`
- Поддержка обоих диалектов SQL

### 5.5.2 Миграция на PostgreSQL ✅ (100%)

#### Описание
Реализована полная миграция с SQLite на PostgreSQL для production окружения. Система автоматически определяет тип БД и использует соответствующий драйвер.

#### Реализованные компоненты

**1. DatabaseConfig**
- Автоматическое определение типа БД (PostgreSQL/SQLite)
- Создание драйвера с правильными настройками
- Интеграция с HikariCP connection pool

**Файл:** `server/api/src/main/kotlin/com/company/ipcamera/server/config/DatabaseConfig.kt`

**Основные функции:**
```kotlin
fun createPostgresDriver(): SqlDriver
fun getDataSource(): HikariDataSource?
fun closeDataSource()
```

**Переменные окружения:**
- `DATABASE_URL` или `POSTGRES_URL` - URL подключения к PostgreSQL
- `DATABASE_USER` - имя пользователя (по умолчанию: postgres)
- `DATABASE_PASSWORD` - пароль (по умолчанию: postgres)
- `DATABASE_MAX_POOL_SIZE` - максимальный размер пула (по умолчанию: 10)

**2. Автоматическое определение БД**
Система автоматически выбирает тип БД:
- Если установлена `DATABASE_URL` или `POSTGRES_URL` → PostgreSQL
- Иначе → SQLite (для desktop/локальной разработки)

**3. Fallback механизм**
- При ошибке подключения к PostgreSQL система логирует предупреждение
- При ошибке миграций Flyway используется fallback на SQLDelight schema creation

#### Зависимости
```kotlin
// PostgreSQL driver
implementation("org.postgresql:postgresql:42.7.3")
implementation("app.cash.sqldelight:jdbc-driver:2.0.3")
```

#### Статус миграции
- ✅ Все SQL запросы обновлены для PostgreSQL
- ✅ DatabaseConfig создан и настроен
- ✅ Автоматическое определение типа БД работает
- ✅ Fallback механизм реализован

### 5.5.3 Connection Pooling ✅ (100%)

#### Описание
Реализован connection pooling через HikariCP для оптимизации производительности и управления соединениями с БД.

#### Конфигурация HikariCP

**Основные параметры:**
- `maximumPoolSize`: настраивается через `DATABASE_MAX_POOL_SIZE` (по умолчанию: 10)
- `minimumIdle`: автоматически рассчитывается как 25% от максимума (минимум 2)
- `connectionTimeout`: 30 секунд
- `idleTimeout`: 10 минут
- `maxLifetime`: 30 минут
- `leakDetectionThreshold`: 1 минута
- `validationTimeout`: 5 секунд
- `keepaliveTime`: 5 минут (проверка соединений)

**PostgreSQL-специфичные настройки:**
- `cachePrepStmts`: true - кэширование prepared statements
- `prepStmtCacheSize`: 250 - размер кэша prepared statements
- `prepStmtCacheSqlLimit`: 2048 - лимит размера SQL для кэша
- `useServerPrepStmts`: true - использование server-side prepared statements
- `rewriteBatchedStatements`: true - оптимизация batch операций
- `cacheResultSetMetadata`: true - кэширование метаданных результатов
- `cacheServerConfiguration`: true - кэширование конфигурации сервера
- `elideSetAutoCommits`: true - оптимизация auto-commit
- `maintainTimeStats`: false - отключение статистики времени

**JMX мониторинг:**
- `registerMbeans`: true - включен JMX для мониторинга пула

#### Файлы реализации
- `server/api/src/main/kotlin/com/company/ipcamera/server/config/DatabaseConfig.kt`

#### Оптимизация
- Автоматический расчет `minimumIdle` на основе `maximumPoolSize`
- Оптимизированные таймауты для production
- Настройки для максимальной производительности PostgreSQL

### 5.5.5 Мониторинг базы данных ✅ (100%)

Реализован сервис мониторинга состояния базы данных и connection pool.

#### Компоненты

**1. DatabaseMonitoringService**
Сервис для получения статистики и проверки состояния БД.

**Файл:** `server/api/src/main/kotlin/com/company/ipcamera/server/service/DatabaseMonitoringService.kt`

**Основные функции:**
```kotlin
suspend fun getPoolStats(): PoolStats
suspend fun checkConnection(): ConnectionHealth
suspend fun getMigrationInfo(): MigrationInfo
```

**2. PoolStats**
Статистика connection pool:
- `activeConnections` - активные соединения
- `idleConnections` - простаивающие соединения
- `totalConnections` - общее количество соединений
- `threadsAwaitingConnection` - потоки, ожидающие соединения
- `maxPoolSize` - максимальный размер пула
- `minIdle` - минимальное количество idle соединений
- `connectionTimeout` - таймаут подключения
- `idleTimeout` - таймаут простоя
- `maxLifetime` - максимальное время жизни соединения
- `utilizationPercent` - процент использования пула
- `isHealthy` - здоровье пула (utilization < 80% и нет ожидающих потоков)

**3. ConnectionHealth**
Состояние подключения к БД:
- `isHealthy` - здоровье подключения
- `databaseName` - имя базы данных
- `autoCommit` - режим auto-commit
- `error` - сообщение об ошибке (если есть)
- `timestamp` - время проверки

**4. API Endpoints**
- `GET /api/v1/database/pool/stats` - статистика connection pool
- `GET /api/v1/database/health` - проверка здоровья БД
- `GET /api/v1/database/migrations` - информация о миграциях

**Файл:** `server/api/src/main/kotlin/com/company/ipcamera/server/routing/DatabaseRoutes.kt`

#### Интеграция с Health Checks
Мониторинг БД интегрирован в общие health checks:

### 5.5.6 Резервное копирование ✅ (100%)

#### Описание
Реализован сервис для создания и восстановления резервных копий базы данных PostgreSQL.

#### Компоненты

**1. DatabaseBackupService**
Сервис для управления резервными копиями БД.

**Файл:** `server/api/src/main/kotlin/com/company/ipcamera/server/service/DatabaseBackupService.kt`

**Основные функции:**
```kotlin
suspend fun createBackup(customName: String? = null): Result<Path>
suspend fun restoreBackup(backupPath: Path): Result<Unit>
suspend fun listBackups(): List<BackupInfo>
suspend fun cleanupOldBackups(keepDays: Int = 30): Int
```

**2. Создание резервных копий**
- Использует `pg_dump` для создания резервных копий
- Формат: custom format (сжатый) - `.sql` или `.dump`
- Автоматическое именование с timestamp
- Поддержка кастомных имен файлов

**3. Восстановление из резервных копий**
- Использует `pg_restore` для восстановления
- Опция `-c` (clean) - удаление объектов перед восстановлением
- Валидация существования файла резервной копии

**4. Управление резервными копиями**
- Список всех резервных копий
- Автоматическая очистка старых бэкапов (по умолчанию: 30 дней)
- Информация о размере и дате создания

**5. API Endpoints**
- `POST /api/v1/database/backup` - создать резервную копию
- `GET /api/v1/database/backup` - список резервных копий
- `POST /api/v1/database/backup/restore` - восстановить из резервной копии
- `POST /api/v1/database/backup/cleanup` - очистка старых бэкапов

**6. BackupInfo**
Информация о резервной копии:
- `fileName` - имя файла
- `path` - путь к файлу
- `size` - размер файла
- `createdAt` - время создания

#### Требования
- `pg_dump` и `pg_restore` должны быть доступны в PATH
- Переменная окружения `PGPASSWORD` устанавливается автоматически

#### Конфигурация
- `backupDirectory`: директория для хранения бэкапов (по умолчанию: `backups/database`)
- `keepDays`: количество дней для хранения бэкапов (по умолчанию: 30)

#### Статус
- ✅ Создание резервных копий работает
- ✅ Восстановление из резервных копий реализовано
- ✅ Список резервных копий доступен

### Резервное копирование

#### POST /api/v1/database/backup
Создать резервную копию БД.

**Параметры запроса (опционально):**
```json
{
  "customName": "backup_before_update.sql"
}
```

**Ответ:**
```json
{
  "success": true,
  "backupPath": "backups/database/backup_ipcss_2026-01-26_12-00-00.sql"
}
```

#### GET /api/v1/database/backup
Получить список резервных копий.

**Ответ:**
```json
{
  "backups": [
    {
      "fileName": "backup_ipcss_2026-01-26_12-00-00.sql",
      "path": "backups/database/backup_ipcss_2026-01-26_12-00-00.sql",
      "size": 1048576,
      "createdAt": 1706284800000
    }
  ]
}
```

#### POST /api/v1/database/backup/restore
Восстановить БД из резервной копии.

**Параметры запроса:**
```json
{
  "backupPath": "backups/database/backup_ipcss_2026-01-26_12-00-00.sql"
}
```

**Ответ:**
```json
{
  "success": true,
  "message": "Database restored successfully"
}
```

#### POST /api/v1/database/backup/cleanup
Очистить старые резервные копии.

**Параметры запроса (опционально):**
```json
{
  "keepDays": 30
}
```

**Ответ:**
```json
{
  "success": true,
  "deletedCount": 5
}
```
