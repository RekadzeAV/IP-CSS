План реорганизации и доработки проекта IP-CSS (для одного разработчика)
Вводные замечания
Роль: единственный разработчик (full-stack, включая C++, Kotlin, DevOps).

Цель: получить стабильную, функциональную систему видеонаблюдения, готовую к пилотному внедрению.

Принципы:

Итеративность: каждый этап должен давать работающий инкремент продукта.

Приоритеты: сначала критическое ядро (видео), потом улучшения.

Автоматизация: активно использовать скрипты, Docker, CI для уменьшения рутины.

Документирование: вести документацию по ходу, чтобы не забыть детали.

Общая продолжительность (оценка): при полной занятости (40 часов в неделю) — около 4–6 месяцев. Реалистичнее разбить на этапы по 2–4 недели.

Этап 0: Подготовка и инфраструктура (1–2 недели)
Цель: создать основу для эффективной разработки без постоянных отвлечений на окружение.

1.3.3. Связывание RTSP-клиента с MediaMTX

Два подхода:

Push: RTSP-клиент после открытия потока перенаправляет его в MediaMTX (публикует). Для этого нужно, чтобы клиент умел выступать в роли источника RTSP.

Pull: MediaMTX сам забирает поток с камеры по команде от Ktor.

Проще реализовать push: доработать C++ rtsp_client, чтобы он после открытия потока подключался к MediaMTX как издатель (используя FFmpeg для отправки). Но это сложнее.

Рекомендация: начать с pull. При старте записи или просмотра Ktor отправляет команду MediaMTX через его API (REST) добавить источник. MediaMTX умеет перехватывать RTSP-потоки (pull). Тогда RTSP-клиент не нужен для трансляции — только для записи. Но для live-просмотра нужен будет доступ к HLS от MediaMTX.

Компромисс: использовать RTSP-клиент только для записи, а для live использовать встроенный в камеры RTSP, но проксировать через MediaMTX (pull). Это упрощает: не нужно писать push-логику. Тогда RTSP-клиент не участвует в live, только в записи. Запись можно вести либо через FFmpeg напрямую (из RTSP-клиента), либо через MediaMTX (если он пишет). MediaMTX умеет записывать в MP4 (опция record). Тогда вообще можно отказаться от своего RTSP-клиента для записи, используя встроенные возможности MediaMTX.

Решение: Использовать MediaMTX как единую точку: он забирает потоки с камер (pull) по команде, транслирует их (HLS/WebRTC) и может записывать. Тогда свой RTSP-клиент нужен только для нетривиальных случаев (если камера не отдает RTSP стабильно). Это сильно упрощает задачу. Принимаем: полагаемся на MediaMTX для live и записи. Тогда задача RTSP-клиента отпадает. Но нужно убедиться, что MediaMTX поддерживает все нужные кодеки и запись. Да, поддерживает.

Пересмотр: Отказываемся от разработки собственного RTSP-клиента для live, используем MediaMTX как прокси и рекордер. Тогда основные усилия уходят на интеграцию MediaMTX и ONVIF.

Добавить проверку доступности потока.

Результат: live-просмотр через веб и запись по расписанию через MediaMTX.

1.4. Реализация записи (2 недели)
Если используем MediaMTX для записи:

Настроить MediaMTX на запись всех потоков или по команде.

Через API Ktor управлять записью: включать/выключать запись для конкретной камеры. MediaMTX имеет HTTP API для управления записью (через запросы к /v3/...). Нужно изучить.

При старте записи Ktor вызывает API MediaMTX, передавая имя камеры.

После остановки записи (или по расписанию) файл оказывается в директории записей MediaMTX. Нужно отслеживать новые файлы и индексировать их в БД. Можно использовать файловый вотчер или периодически сканировать директорию.

Альтернатива: оставить свой RTSP-клиент для записи (для независимости). Но это увеличивает объем работ.

Выбор: Использовать MediaMTX для записи, это быстрее и надежнее. Для записи потребуется доработка RTSP-клиента не нужна. Однако, если камера требует аутентификации, MediaMTX должен уметь её передавать. В конфиге можно задать логин/пароль для каждого пути. Значит, при добавлении камеры через ONVIF мы получаем RTSP URL с уже встроенными credentials? Обычно да: rtsp://user:pass@ip/.... MediaMTX поддерживает такие URL. Тогда все хорошо.

Итак, отказываемся от разработки собственного RTSP-клиента. Сэкономленное время направляем на ONVIF и MediaMTX.
