Начальные действия перед стартом разработки
Перед началом активной разработки необходимо выполнить следующие шаги для сохранения текущего состояния проекта и создания изолированных веток для новых изменений:

Создать резервную ветку main-old
Текущая кодовая база (альфа-версия) будет скопирована в ветку main-old для сохранности. Это позволит в любой момент вернуться к исходному состоянию или использовать фрагменты старого кода для справки.

bash
git checkout main
git pull origin main
git checkout -b main-old
git push origin main-old
git checkout main
Создать основную ветку разработки develop
Вся новая работа будет вестись в ветке develop, куда будут сливаться промежуточные результаты. Вся новая структура и код создаются здесь с нуля, старый код не переносится, а служит только для справки.

Создать отдельную ветку для интеграции MediaMTX main-M-MTX
Поскольку работа с медиа-сервером затрагивает критическую функциональность и может быть долгой, она будет вестись в изолированной ветке main-M-MTX. После завершения и стабилизации ветка будет влита в develop.

Написать C++ обертки:

std::vector<std::string> discoverCameras(int timeout_ms) — возвращает IP-адреса.

(дополнительно) функции для PTZ.

Скомпилировать как статическую библиотеку (libonvif_wrapper.a).

Создать onvif.def для Kotlin/Native cinterop.

В shared создать класс OnvifDiscover с вызовом нативных функций.

Интегрировать с новым DiscoverCamerasUseCase (будет создан).

1.2. Настройка MediaMTX (2 недели)
Добавить сервис mediamtx в docker-compose.yml.

Создать конфиг mediamtx.yml:

yaml
rtspAddress: :8554
hlsAddress: :8888
webrtcAddress: :8889
authMethod: external

Пробросить volumes для записей: ./recordings:/recordings.

Настроить сеть между контейнерами.

1.3. Интеграция аутентификации MediaMTX с Ktor
В Ktor создать эндпоинт GET /api/auth/stream (или POST), который MediaMTX вызывает для проверки. MediaMTX отправляет Basic Auth (логин/пароль). Логин — имя пользователя (например, streamer), пароль — JWT-токен.

Реализовать проверку: извлечь JWT из пароля, проверить подпись, убедиться в праве доступа к камере (имя потока = ID камеры).

Вернуть 200 OK при успехе, иначе 401.

Создать компонент HLSPlayer, принимающий cameraId.

Формировать URL: http://mediamtx:8888/cameraId/index.m3u8 (для браузера использовать localhost с пробросом портов).

Добавить обработку ошибок и состояния загрузки.

(Опционально) использовать существующие наработки веб-интерфейса из старой версии, адаптировав их под новую схему.

1.5. Реализация записи через MediaMTX и индексация файлов
MediaMTX может записывать все публикуемые потоки автоматически (record: yes). Файлы сохраняются в формате YYYY-MM-DD_HH-MM-SS.mp4 в поддиректориях по дате.

Организовать индексацию записей в БД. Рекомендуемый подход: гибридный — использовать файловый вотчер (WatchService) для быстрого обнаружения новых файлов и периодическое полное сканирование для подстраховки. Реализация на Kotlin с корутинами (см. детали в разделе "Реализация сканирования директории записей").

Создать фоновый процесс в Ktor (корутина), выполняющий сканирование и добавление записей в таблицу recordings.

Для каждой записи сохранять: camera_id, file_path, start_time, end_time (из имени файла или метаданных, end_time можно обновлять после завершения записи).

Добавить эндпоинты для управления записью (start/stop), которые отправляют команды в MediaMTX через его API (например, POST /v3/paths/{cameraId}/startrecord).

1.6. Интеграция с PostgreSQL
В shared настроить SQLDelight с диалектом postgresql.

Создать таблицы:

sql
CREATE TABLE cameras (id UUID PRIMARY KEY, name TEXT, ip TEXT, username TEXT, password TEXT, rtsp_url TEXT, ...);
CREATE TABLE recordings (id UUID PRIMARY KEY, camera_id UUID, file_path TEXT, start_time TIMESTAMP, end_time TIMESTAMP, hash_sha256 TEXT, xxhash64 BIGINT, last_check TIMESTAMP);
CREATE TABLE events (...);
CREATE TABLE users (...);
CREATE TABLE settings (...);
Реализовать репозитории с использованием SQLDelight.

Настроить миграции (Flyway или создание таблиц при старте).

4.2. Поддержка устройств ввода/вывода (I/O)
Модели данных:

IODevice (id, name, type: gpio/usb, platform, ports)

InputPort (id, device_id, index, current_state: boolean, last_changed)

OutputPort (id, device_id, index, state, mode: momentary/latched)

Интеграция с GPIO на Raspberry Pi: использовать библиотеку WiringPi (или pigpio), написать C++ обертку.

Интеграция с USB-реле: использовать libusb, написать обертку для популярных моделей.

C++ обертки и cinterop: создать классы GpioController, UsbRelayController с методами readInput(int pin), writeOutput(int pin, bool value). Предоставить единый фасад.

Интеграция в правила (action rules): в shared добавить сущности Rule, Condition, Action. Реализовать движок правил (простой: при событии проверять условия и выполнять действия).

UI для настройки I/O: в Next.js создать страницу "Устройства I/O" с отображением состояния портов, возможностью ручного переключения. Добавить редактор правил (drag-n-drop или простой визуальный конструктор).

4.4. Улучшения безопасности и соответствие ГОСТ
Ролевая модель: добавить в таблицу users поле role (admin, auditor, viewer). Во всех API проверять права.

2FA (TOTP): использовать библиотеку java-totp или kotlin-totp. При включении 2FA генерировать секрет, показывать QR-код. При логине проверять код.

Контрольные суммы и проверка целостности:

При завершении записи вычислять SHA-256 и xxHash64, сохранять в таблице recordings.

Реализовать фоновый процесс для периодической проверки целостности записей с использованием xxHash64 (быстрый хеш) и обновлением поля last_check. Проверки выполнять ночью, батчами, с паузами для снижения нагрузки на диск. (см. детали в разделе "Реализация проверки целостности").

Аудит лог: создать таблицу audit_log (user_id, action, timestamp, details). Логировать все значимые действия.

4.5. Экспорт в AXF
Изучить формат AXF (SMPTE ST 2034-1). Для начала сделать упрощённый экспорт: ZIP-архив, содержащий видеофайл и XML-файл с метаданными.

Приоритет 4: Специальное требование – Интеграция видеоаналитики для управления СКУД
Контекст и цель
Необходимо доработать сервер видеонаблюдения для автоматического управления системами контроля доступа (СКУД) и автоматическими воротами/шлагбаумами. Основная цель — обеспечить беспрепятственный и приоритетный проезд автомобилям спецслужб (скорая помощь, полиция, МЧС, пожарные) без участия человека.

Базовый сценарий работы
Автомобиль скорой помощи (или другой спецтранспорт) подъезжает к закрытому шлагбауму в зону видимости камеры.

Система в реальном времени анализирует видеопоток и аудиопоток.

При одновременном срабатывании двух триггеров:

Визуальное подтверждение: обнаружены включенные проблесковые маячки синего (или красного) цвета на крыше автомобиля.

Аудиоподтверждение: зафиксирован характерный звуковой сигнал сирены.

Сервер формирует управляющий сигнал на открытие шлагбаума (через реле или HTTP-команду).

Шлагбаум открывается, автомобиль проезжает.

Система логирует событие с сохранением видеофрагмента.

Технические требования
Модуль видеоаналитики (детекция спецсигналов):

Распознавание типа ТС по форме и расположению маячков.

Анализ цвета и частоты мигания (синий/красный).

Работа в любое время суток (ночью детекция по ярким источникам, игнорируя фары).

Модуль аудиоаналитики (детекция звука сирены):

Различение звука сирены от общего шума.

Подавление ложных срабатываний от похожих тональных сигналов.

Желательно учитывать приближение звука (увеличение громкости).

Логика принятия решения:

Условие «И»: сигнал на открытие только при одновременном срабатывании обоих детекторов в течение 3–5 секунд.

Приоритет над обычными очередями вызова.

Анти-зацикливание: режим ожидания после открытия на время проезда.

Интеграция с оборудованием:

Тип сигнала: через низковольтное реле (сухой контакт) или HTTP-команду на IP-контроллер шлагбаума.

Совместимость с популярными моделями (Came, Doorhan, Nice и др.).

Интерфейс и отчетность:

Возможность включения/отключения функции «Автопропуск спецтранспорта».

История событий с привязкой скриншота или 10-секундного видео.

Критерии приемки
Тест «Скорая помощь»: автомобиль с маячками и сиреной подъезжает → шлагбаум открывается.

Тест на ложное срабатывание (днем): обычный автомобиль с громкой музыкой и аварийкой → шлагбаум закрыт.

Тест на ложное срабатывание (ночью): автомобиль с яркими фарами → шлагбаум закрыт.

Тест «Тихий проезд»: скорая с маячками, но без сирены → шлагбаум закрыт.

Тест «Транзит»: скорая с сиреной проезжает мимо, не останавливаясь → шлагбаум закрыт.

Проблема
MediaMTX сохраняет записи в файловую систему. Нам необходимо отслеживать появление новых файлов и добавлять записи о них в базу данных (таблицу recordings). Нужно сделать это эффективно, без постоянной высокой нагрузки на диск и процессор.

Рекомендуемое решение: гибридный подход (WatchService + периодическое сканирование)

kotlin
// Модуль: server-jvm/infrastructure
import kotlinx.coroutines.*
import java.io.IOException
import java.nio.file.*
import java.nio.file.StandardWatchEventKinds.*
import java.util.concurrent.ConcurrentHashMap

class RecordingScanner(
    private val recordingsDir: Path,
    private val onNewFile: suspend (Path) -> Unit,
    private val scanIntervalMinutes: Long = 60,
    private val stabilizationDelayMs: Long = 5000 // ждём 5 сек после создания
) {
    private val scope = CoroutineScope(Dispatchers.IO + SupervisorJob())
    private val recentlySeen = ConcurrentHashMap.newKeySet<String>()

    fun start() {
        scope.launch { watchForNewFiles() }
        scope.launch { periodicFullScan() }
    }

    fun stop() {
        scope.cancel()
    }

    private suspend fun watchForNewFiles() = withContext(Dispatchers.IO) {
        try {
            val watchService = FileSystems.getDefault().newWatchService()
            recordingsDir.register(watchService, ENTRY_CREATE, ENTRY_MODIFY)

            while (isActive) {
                val key = watchService.take()
                for (event in key.pollEvents()) {
                    if (event.kind() == OVERFLOW) continue
                    val fileName = event.context() as Path
                    val fullPath = recordingsDir.resolve(fileName)
                    if (Files.isRegularFile(fullPath) && fileName.toString().endsWith(".mp4")) {
                        scope.launch { processFileAfterStabilization(fullPath) }
                    }
                }
                key.reset()
            }
        } catch (e: IOException) {
            println("WatchService не доступен: ${e.message}. Будет использоваться только периодическое сканирование.")
        }
    }

    private suspend fun processFileAfterStabilization(path: Path) {
        val pathStr = path.toString()
        if (!recentlySeen.add(pathStr)) return

        delay(stabilizationDelayMs)
        var lastSize = -1L
        repeat(3) {
            val currentSize = Files.size(path)
            if (currentSize == lastSize) {
                recentlySeen.remove(pathStr)
                onNewFile(path)
                return
            }
            lastSize = currentSize
            delay(1000)
        }
        recentlySeen.remove(pathStr)
    }

    private suspend fun periodicFullScan() = withContext(Dispatchers.IO) {
        while (isActive) {
            delay(scanIntervalMinutes * 60 * 1000)
            fullScan()
        }
    }

    private suspend fun fullScan() {
        Files.walk(recordingsDir)
            .filter { Files.isRegularFile(it) && it.toString().endsWith(".mp4") }
            .forEach { path ->
                scope.launch { onNewFile(path) }
            }
    }
}

Почему этот подход эффективен?

WatchService даёт почти реальное время, не нагружая диск.

Задержка стабилизации исключает индексацию недописанных файлов.

Периодическое полное сканирование — подстраховка на случай пропущенных событий.

Корутины обеспечивают асинхронность без блокировок.

Реализация проверки целостности файлов (контрольные суммы)
Проблема
Для обеспечения целостности записей нужно периодически проверять, что файлы не были изменены. Полное чтение файлов для вычисления SHA-256 создаёт высокую нагрузку.

Рекомендуемое решение: использовать быстрый хеш xxHash64 и проверять ночью батчами

При завершении записи вычисляем SHA-256 (однократно) и xxHash64, сохраняем в БД.

Фоновый процесс раз в сутки выбирает записи, у которых last_check давно, и пересчитывает xxHash64, сравнивая с сохранённым.

Проверка выполняется с паузами между файлами, чтобы не нагружать диск.

kotlin
// Вспомогательный объект для хеширования
import net.jpountz.xxhash.XXHashFactory
import java.io.FileInputStream
import java.security.MessageDigest
import java.nio.file.Path

object FileHasher {
    private val xxHashFactory = XXHashFactory.fastestJavaInstance()

    fun sha256(file: Path): String {
        val digest = MessageDigest.getInstance("SHA-256")
        FileInputStream(file.toFile()).use { fis ->
            val buffer = ByteArray(8192)
            var read: Int
            while (fis.read(buffer).also { read = it } != -1) {
                digest.update(buffer, 0, read)
            }
        }
        return digest.digest().joinToString("") { "%02x".format(it) }
    }

    fun xxHash64(file: Path): Long {
        val hasher = xxHashFactory.newStreamingHash64(0)
        FileInputStream(file.toFile()).use { fis ->
            val buffer = ByteArray(8192)
            var read: Int
            while (fis.read(buffer).also { read = it } != -1) {
                hasher.update(buffer, 0, read)
            }
        }
        return hasher.getValue()
    }
}
Периодическая проверка

kotlin
class IntegrityChecker(
    private val recordingRepository: RecordingRepository,
    private val batchSize: Int = 100,
    private val checkIntervalHours: Long = 24
) {
    private val scope = CoroutineScope(Dispatchers.IO + SupervisorJob())

    fun start() {
        scope.launch { periodicCheck() }
    }

    fun stop() {
        scope.cancel()
    }

    private suspend fun periodicCheck() = withContext(Dispatchers.IO) {
        while (isActive) {
            val now = Instant.now()
            val nextCheck = now.atZone(ZoneId.systemDefault())
                .withHour(2).withMinute(0).withSecond(0)
                .toInstant()
            val delay = if (nextCheck > now) Duration.between(now, nextCheck).toMillis()
                        else Duration.between(now, nextCheck.plus(1, ChronoUnit.DAYS)).toMillis()
            delay(delay)

            checkIntegrity()
        }
    }

    private suspend fun checkIntegrity() {
        var offset = 0
        do {
            val recordings = recordingRepository.getRecordingsForIntegrityCheck(offset, batchSize)
            if (recordings.isEmpty()) break

            for (rec in recordings) {
                val file = Paths.get(rec.filePath)
                if (!Files.exists(file)) {
                    recordingRepository.markIntegrityFailed(rec.id, "File missing")
                    continue
                }
                try {
                    val currentHash = FileHasher.xxHash64(file)
                    if (currentHash != rec.xxHash64) {
                        recordingRepository.markIntegrityFailed(rec.id, "Hash mismatch")
                    } else {
                        recordingRepository.updateLastCheck(rec.id, Instant.now())
                    }
                } catch (e: Exception) {
                    recordingRepository.markIntegrityFailed(rec.id, e.message)
                }
            }
            offset += batchSize
            delay(1000) // пауза между батчами
        } while (true)
    }
}

Пояснения к ключевым директориям
core/ – все нативные компоненты. Каждая поддиректория содержит CMakeLists.txt для сборки отдельной библиотеки. Скрипты build_*.sh/ps1 упрощают компиляцию под целевую платформу. Готовые библиотеки складываются в core/out/lib/{os}-{arch} и затем подключаются к shared через cinterop.

shared/ – основной модуль Kotlin Multiplatform. Здесь лежит бизнес-логика, доменные модели, интерфейсы репозиториев, а также SQLDelight-запросы. Папка nativeInterop содержит .def файлы, описывающие нативные функции для Kotlin/Native.

platforms/server-jvm/ – серверное приложение. Разделено на слои: api (маршруты Ktor), core (сервисы), infrastructure (работа с БД, внешние API). Такая структура облегчает тестирование и поддержку.

platforms/web/ – фронтенд на Next.js. Папка api/generated будет заполняться автоматически при генерации клиента из OpenAPI-спецификации.

integration-tests/ – модуль для тестов, требующих поднятия реальных сервисов (БД, MediaMTX). Использует Testcontainers.

scripts/ – все скрипты для установки, настройки и сборки. Это помогает новым разработчикам быстро развернуть окружение.

docker-compose.yml – описывает все сервисы, необходимые для работы системы: PostgreSQL, MediaMTX, ai-engine (Python микросервис), а также сам сервер (опционально). Переменные окружения подгружаются из .env.

Общие требования к ответам агента (AI-ассистента)
Приводи код с комментариями на русском и английском языках (по ситуации), чтобы код был понятен широкой аудитории и мог использоваться в международной среде.

Для Gradle-скриптов, Dockerfile, конфигураций давай полные листинги – это позволяет разработчику скопировать их и сразу применить.

Объясняй, почему предлагается то или иное решение – важно понимать мотивацию и альтернативы.

Если нужно выбирать между несколькими вариантами, опиши плюсы и минусы каждого.

Давай ссылки на документацию или примеры, если это уместно, чтобы разработчик мог углубиться.

Учитывай кроссплатформенность (Linux, Windows, macOS) – решения должны работать на всех целевых ОС.

Помни, что разработчик может не иметь глубоких знаний в определенных областях (C++, ONVIF), поэтому объясняй шаги подробно.

Предлагай максимально эффективные пути, используй готовые библиотеки, избегай излишней сложности.

Все решения должны быть реализуемы одним разработчиком в разумные сроки – предлагай реалистичные сроки и декомпозицию.

Если задача слишком сложна, предложи упрощенный вариант, который можно улучшить позже, либо предложи декомпозицию задачи на более мелкие подзадачи. Это поможет не увязнуть в деталях и сохранить прогресс.
