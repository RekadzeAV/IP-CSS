# Аудит видеопараметров IP-CSS и формулировки для ТЗ (отраслевой чеклист 2026)

**Назначение:** зафиксировать фактические параметры проекта IP-CSS, сопоставить их с чеклистом из промта аудита (разрешение, FPS, кодеки, ONVIF, плотность пикселей по IEC 62676-4, ИИ/облако) и дать **готовые к вставке** формулировки для ТЗ/спецификации с приоритетом внедрения.

**Оговорка:** ссылки на конкретные редакции ГОСТ/IEC в промте нужно **перепроверять по официальным текстам НД** перед договорной фиксацией; здесь зафиксированы **проектные** требования, вытекающие из чеклиста аудита и здравого смысла для продуктовой дорожной карты.

## 2. Текущие параметры проекта IP-CSS (по репозиторию)

### 2.1. Разрешение и качество потоков (HLS-транскод на сервере)

Источник: `HlsGeneratorService.kt` — варианты `StreamQuality`:

| Уровень | Разрешение | FPS (выход HLS) |
|---------|------------|-----------------|
| LOW | 640×360 | 15 |
| MEDIUM | 1280×720 | 25 |
| HIGH | 1920×1080 | 30 |
| ULTRA | 1920×1080 | 30 (повышенный битрейт) |

**Вывод:** в цепочке **адаптивного HLS по умолчанию** нет профиля **2560×1440 (2K)** и **3840×2160 (4K)**. Модель `Resolution` и тесты допускают произвольные ширину/высоту (в т.ч. 4K для камеры/записи), но **готовый пользовательский профиль HLS** до 4K не доведён.

### 2.2. Модель камеры (дефолты и аналитика)

Источник: `shared/.../Camera.kt`, `AnalyticsSettings`:

- **FPS по умолчанию:** 25 (`Camera.fps`).
- **Кодек по умолчанию:** строка `"H.264"`.
- **Аналитика:** движение (вкл.), детекция объектов / ANPR / лица / поведение / плотность толпы — **флаги и пороги есть**, по умолчанию часть выключена (`objectDetection`, `anprEnabled`, `faceRecognition`, … — `false` где указано).

### 2.3. Кодеки (запись / натив / декодер)

- **Нативный стек и FFmpeg-энкодер:** поддержка **H.264, H.265, MJPEG** (`native/video-processing`, `VideoDecoderImpl` — H.264/H.265).
- **Документация:** `docs/VIDEO_CODECS.md` — H.264 позиционируется как рекомендация «для большинства случаев» записи; H.265 — для экономии места.
- **HLS:** транскод **видео в `libx264`** (H.264), не HEVC в типовом пути.

### 2.4. ONVIF и события

- Клиент и типы ONVIF присутствуют в дереве (`OnvifClient`, документация `ONVIF_CLIENT.md`, планы по WS-Discovery / Digest в `docs/status/ПЛАН_СЕТЕВОЙ_СЛОЙ_2026.md`).
- Подписки на события ONVIF интегрированы в серверный контур (см. `MVP_PHASED_IMPLEMENTATION_PLAN.md`).

### 2.5. IEC 62676-4 / плотность пикселей (px/m)

- В доменной модели **нет** явных полей «расстояние до объекта», «требуемый класс идентификации», **px/m** для привязки к сцене.
- В аналитике есть пороги в пикселях/модели, но не **инженерный расчёт покрытия** под стандарт наблюдения.

### 2.6. VSaaS / облако / IoT

- В репозитории есть планы по облаку/синхронизации (`CLOUD_SYNC_AND_STORAGE.md` и др.); **единый продуктовый контур VSaaS** как в промте не описан как обязательная часть MVP в этом документе.

## 3. Пробелы относительно чеклиста промта

| № | Тема | Статус в IP-CSS |
|---|------|-----------------|
| 1 | **2K (2560×1440)** как обязательный массовый профиль трансляции/архива | Не задан в HLS-качествах; нет явного ТЗ-уровня. |
| 2 | **4K** как целевой профиль для ответственных зон | Нет HLS-профиля 4K; запись/камера могут быть 4K, UI/путь не нормирован. |
| 3 | **FPS:** зона «только 12–15» vs **20–25** как отраслевой минимум для большинства объектов | LOW=15 ок для обзора; нет политики зон/классов объекта в продукте. |
| 4 | **30–60+ FPS** для спецсцен (кассы, транспорт) | Нет отдельных пресетов/ограничений в ТЗ продукта. |
| 5 | **HEVC для 2K/4K** в дистрибуции (HLS/архив) | HLS сейчас **H.264**; HEVC есть в декоде/нативе, но не как обязательная цепочка для высоких разрешений. |
| 6 | **H.266 / VVC** | Не фигурирует; разумно как перспектива. |
| 7 | **ONVIF** | Есть; нужно ТЗ: минимальный профиль устройств, тестируемые сервисы. |
| 8 | **IEC 62676-4 — px/m** | Нет модели сцены и требований к идентификации в ТЗ. |
| 9 | **ИИ + облако** | ИИ описан в `AI_ANALYTICS.md`; связка с VSaaS/мультитенантностью не сведена в один нормативный документ продукта. |

## 4. Готовые формулировки для ТЗ/спецификации (копипаст)

Для каждого пункта: **формулировка** и **приоритет** (критично / рекомендовано / перспективно).

### 4.1. Разрешение и профили потока

**Приоритет: рекомендовано** (для коммерческого позиционирования «умный дом» / ответственные зоны)

> Система SHALL поддерживать минимум следующие **профили выходного потока** (трансмакс / HLS или эквивалент): (1) обзорный **не ниже 1280×720**; (2) основной **1920×1080**; (3) для объектов класса «умный дом» и периметра с требованием детализации — **2560×1440** при наличии исходного потока не ниже этого разрешения; (4) для зон идентификации лиц/мелких объектов — **3840×2160** при поддержке канала и клиентского декодера. Для каждого профиля SHALL быть задокументированы битрейт, GOP и целевой FPS.

**Приоритет: критично** (если контракт с оператором жёсткий по Full HD)

> Для всех каналов реального времени SHALL обеспечиваться профиль **не хуже 1920×1080@20 FPS** на основном потоке, если камера отдаёт не менее указанных параметров; снижение до 1280×720@12–15 FPS допускается **только** для потоков, явно помеченных как «низкозначимый обзор» в конфигурации объекта.

### 4.2. Частота кадров по классам зон

**Приоритет: рекомендовано**

> Конфигурация объекта SHALL классифицировать зоны наблюдения: **A** (общий обзор), **B** (стандартное наблюдение), **C** (событийные: кассы, транспортные ворота, зоны выдачи). Для зон **B** целевой FPS SHALL быть **20–25** на записи и на превью оператора; для зон **C** — **не менее 30 FPS** на основном потоке при поддержке оборудования; **60 FPS** — опционально по согласованию и профилю оборудования.

### 4.3. Кодеки и архив

**Приоритет: критично** (для новых внедрений 2K/4K и экономии хранилища)

> Для записи архива с разрешением **выше 1920×1080** система SHALL использовать **H.265 (HEVC)** или кодек с **не худшей** эффективностью при сопоставимом качестве; **H.264** допускается для **legacy-устройств** и для разрешений **до Full HD включительно**, с явной пометкой в паспорте объекта.

**Приоритет: рекомендовано** (для HLS)

> Адаптивный поток SHALL включать как минимум одну HEVC-рендцию для клиентов с поддержкой **hvc1/hevc** в контейнере fMP4/CMAF (или эквивалент, согласованный с клиентами); при отсутствии поддержки на клиенте SHALL выполняться откат на H.264-профиль с тем же уровнем качества по метрикам (PSNR/SSIM/VMAF — по согласованию).

**Приоритет: перспективно**

> В дорожной карте на 2–3 года SHALL быть зарезервирован анализ **H.266 (VVC)** для сценариев **8K** и крайне ограниченных каналов; внедрение не является обязательством текущей версии продукта.

### 4.4. ONVIF

**Приоритет: критично** (для IP-оборудования)

> Подключаемое IP-оборудование SHALL поддерживать **ONVIF** не ниже согласованного профиля (Device Management, Media, Events; PTZ — при наличии функции). Система SHALL проходить приёмочные тесты на совместимость с перечнем эталонных моделей из приложения к ТЗ.

### 4.5. IEC 62676-4 и плотность пикселей

**Приоритет: рекомендовано** (инженерное проектирование, не только ПО)

> Для каждой камеры и зоны SHALL храниться расчёт **плотности изображения на метр (px/m)** (или **мм/пиксель** на объекте контроля) на заданной глубине сцены, с привязкой к **классу задачи** (обнаружение / наблюдение / идентификация / распознавание). Программное обеспечение SHALL позволять задавать целевые **px/m** и предупреждать оператора при несоответствии выбранного разрешения/фокусного расстояния расчётным значениям (MVP: ручной ввод расстояния и ширины сцены).

### 4.6. ИИ-аналитика и облако

**Приоритет: рекомендовано**

> Система SHALL поддерживать конвейер **ИИ-аналитики** (детекция объектов, при необходимости ANPR, детекция/идентификация лиц, сценарии аномалий) с конфигурируемым размещением: **на объекте**, **на сервере** заказчика или в **облачном VSaaS**-режиме при наличии договорной модели данных и шифрования каналов.

**Приоритет: перспективно**

> Интеграция с внешними **IoT**-платформами (тревожные входы, СКУД, пожарная сигнализация) SHALL описываться отдельным приложением к ТЗ по API и событийной шине.

## 5. Приоритеты внедрения в продукт IP-CSS (краткая матрица)

| Изменение в продукте | Приоритет |
|---------------------|-----------|
| HLS: профили **2K и 4K**, политика FPS по уровням | Рекомендовано |
| HLS/архив: **HEVC**-ветка при наличии лицензий/железа | Рекомендовано |
| Доменная модель / UI: **px/m**, класс зоны, предупреждения | Рекомендовано |
| Документация ONVIF: закрытие Digest/Discovery по плану сетевого слоя | Критично для заявленной совместимости |
| VVC / 8K | Перспективно |
| VSaaS multi-tenant как обязательный режим | Перспективно (зависит от коммерческой модели) |

## 6. Чего не хватает для «полевого» аудита конкретного объекта

Перед финализацией ТЗ под **конкретную** площадку запросите у заказчика:

- перечень камер с **нативными** разрешениями и кодеками основного/субпотока;
- требуемые **классы идентификации** по зонам и нормативные ссылки, которые договор закрепляет;
- ограничения по **каналу** (Mbps) и **хранилищу** (дней архива);
- список **клиентов** (браузеры, Android, desktop) и требование **HEVC** на каждом.
