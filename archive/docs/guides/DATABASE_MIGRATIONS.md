# Миграции базы данных

## Обзор

Система миграций базы данных реализована для безопасного обновления схемы БД при изменении структуры таблиц. Используется SQLDelight для управления миграциями.

В этом документе описаны: **как добавить миграцию** (пути, шаги, тестирование) и **как проверить откат** — на случай появления стратегии отката в будущем (задача **5.2.2**).

**Источники истины:** `MigrationManager.kt` (`CURRENT_SCHEMA_VERSION`), `shared/.../database/CameraDatabase.sq`.

## Компоненты системы миграций

### MigrationManager

Управляет процессом миграции:
- Определяет текущую и целевую версию БД
- Применяет необходимые миграции
- Валидирует результат миграции

**Использование:**
```kotlin
val currentVersion = MigrationManager.getCurrentVersion(database)
val targetVersion = MigrationManager.getTargetVersion()
MigrationManager.applyMigrations(driver, currentVersion, targetVersion)
```

### MigrationValidator

Валидирует миграцию после её применения:
- Проверяет версию схемы
- Проверяет наличие всех таблиц
- Проверяет целостность данных

**Использование:**
```kotlin
val isValid = MigrationValidator.validateMigration(database, expectedVersion)
```

### MigrationLogger

Логирует процесс миграции:
- Начало/окончание миграции
- Примененные изменения
- Ошибки и предупреждения

## Использование

### Создание новой БД

При создании новой БД система автоматически:
1. Создает схему через `CameraDatabase.Schema.create()`
2. Инициализирует версию схемы в таблице `schema_version`

### Обновление существующей БД

При обновлении существующей БД система:
1. Определяет текущую версию из таблицы `schema_version`
2. Применяет необходимые миграции через `CameraDatabase.Schema.migrate()`
3. Обновляет версию схемы
4. Валидирует результат миграции

### Инициализация в приложении

```kotlin
val databaseFactory = DatabaseFactory(context)
val driver = databaseFactory.createDriver()
val database = createDatabaseSync(driver) // Использует миграции автоматически
```

## Создание новой миграции (чек-лист 5.2.1) и документирование процесса (5.2.2)

Соответствует задачам **5.2.1** и **5.2.2** в `MVP_PHASED_IMPLEMENTATION_PLAN.md`. Ниже описан процесс добавления миграции и проверки отката (на случай появления стратегии отката в будущем).

---

### Как добавить миграцию (кратко)

1. Создать файл миграции `N.sqm` в каталоге миграций (N — следующий порядковый номер).
2. Обновить целевую схему в `CameraDatabase.sq` (новые таблицы/поля/индексы).
3. Увеличить `CURRENT_SCHEMA_VERSION` в `MigrationManager.kt` до N.
4. Собрать проект, прогнать тесты.
5. Обязательно протестировать переход N−1 → N на копии реальной БД (см. [Тестирование миграции с копией БД](#тестирование-миграции-с-копией-бд-обязательно-для-521)).
6. Только после успешной проверки — мержить и выкатывать в прод.

Без пункта 5 миграцию в прод не применять.

---

### Пути к файлам

| Что | Путь |
|-----|------|
| Файлы миграций | `shared/src/commonMain/sqldelight/com/company/ipcamera/shared/database/migrations/N.sqm` |
| Целевая схема | `shared/src/commonMain/sqldelight/com/company/ipcamera/shared/database/CameraDatabase.sq` |
| Версия схемы в коде | `shared/src/commonMain/kotlin/com/company/ipcamera/shared/data/local/MigrationManager.kt` (константа `CURRENT_SCHEMA_VERSION`) |

**При любом изменении схемы** (новые таблицы, поля, индексы) выполните:

| # | Действие | Где |
|---|----------|-----|
| 1 | Добавить файл миграции `N.sqm` | `shared/.../database/migrations/N.sqm`, где N — следующий порядковый номер (после последней миграции) |
| 2 | Обновить `CURRENT_SCHEMA_VERSION` | `shared/.../local/MigrationManager.kt` — присвоить значение N (целевая версия после миграции) |
| 3 | Обновить целевую схему | `shared/.../database/CameraDatabase.sq` — привести в соответствие с новой версией (новые таблицы/поля/индексы) |
| 4 | Протестировать миграцию N-1 → N | Копия реальной БД версии N-1; применить миграцию; проверить версию и целостность (см. ниже) |

Без выполнения пункта 4 миграцию в прод не применять.

### Шаги по шагам

1. Определите изменения схемы (добавление таблиц, полей, индексов и т.д.)
2. Создайте файл миграции `N.sqm` в папке `migrations/`, где N — следующий номер миграции
3. Напишите SQL для миграции
4. Обновите схему `CameraDatabase.sq` с новыми изменениями
5. Обновите `CURRENT_SCHEMA_VERSION` в `MigrationManager.kt`
6. **Протестируйте миграцию с копией реальной БД (версия N-1 → N)** — см. раздел «Тестирование миграции с копией БД»

### Пример миграции

```sql
-- Migration 2: Add password_hash field to user table
-- Version: 2 -> 3
-- Date: 2026-01-XX

ALTER TABLE user ADD COLUMN password_hash TEXT;

-- Инициализация версии 3 после применения миграции
INSERT INTO schema_version(version, applied_at, description)
VALUES (3, strftime('%s', 'now'), 'Added password_hash field to user table');
```

### Важные замечания

1. **Идемпотентность:** Миграции должны быть идемпотентными (можно применить несколько раз без побочных эффектов)
2. **Безопасность:** Не используйте `IF NOT EXISTS` в миграциях - SQLDelight обрабатывает это автоматически
3. **Порядок:** Миграции применяются последовательно, начиная с текущей версии
4. **Откат:** Откат миграций не поддерживается автоматически (см. раздел [Проверка отката](#проверка-отката)).

## Проверка отката (5.2.2)

**Текущее состояние:** автоматический откат (downgrade) миграций **не реализован**. В коде явно запрещён переход на меньшую версию схемы: при `fromVersion > toVersion` в `MigrationManager.applyMigrations()` выбрасывается `IllegalStateException` («Downgrade is not supported»). Единственная безопасная «отмена» после неудачной миграции — восстановление БД из бэкапа, сделанного до применения миграции.

Ниже описан порядок проверки отката **на случай, если в будущем появится стратегия отката** (например, скрипты `N_down.sqm` или ручной downgrade).

### Когда появится стратегия отката

Если будет добавлена поддержка отката, проверку рекомендуется выполнять так:

1. **Перед внедрением отката**
   - Иметь резервную копию БД текущей версии (N) перед применением миграции в прод.
   - Документировать для каждой миграции N: какие объекты созданы/изменены и что нужно откатить (DROP/ALTER), чтобы вернуться к версии N−1.

2. **Проверка отката (рекомендуемый сценарий)**
   - Взять копию БД после успешной миграции N−1 → N (версия N).
   - Применить процедуру отката (скрипт или ручные шаги) до версии N−1.
   - Убедиться, что в `schema_version` записана версия N−1.
   - Проверить: отсутствуют объекты, добавленные миграцией N; данные в общих таблицах не повреждены.
   - При необходимости прогнать приложение с версией кода, ожидающей схему N−1, и проверить базовые сценарии.

3. **Регрессия после отката**
   - Повторно применить миграцию N (N−1 → N) на той же БД и убедиться, что схема снова соответствует версии N и приложение работает.

**Кратко: как проверить откат (когда появится стратегия):** (1) копия БД версии N → применить процедуру отката до N−1; (2) проверить `schema_version` и отсутствие объектов миграции N; (3) при необходимости прогнать приложение со схемой N−1; (4) повторно применить миграцию N и убедиться, что всё работает.

Пока стратегия отката не реализована, единственная безопасная «отмена» после неудачной миграции — восстановление БД из бэкапа, сделанного до применения миграции.

## Тестирование

### Тестирование миграции с копией БД (обязательно для 5.2.1)

Перед выкатом миграции N в прод необходимо проверить переход **N-1 → N** на копии реальной БД:

1. **Сделать копию реальной БД** (файл SQLite или дамп), убедиться, что в ней версия N-1 (в таблице `schema_version` значение `MAX(version) = N-1`).
2. **Подставить копию как источник БД** в тестовом сценарии или временно в приложении (указать путь к копии вместо продакшн-файла).
3. **Запустить приложение или интеграционный тест**, который вызывает `DatabaseFactory.createDatabaseSync(driver)` / `createDatabase(driver)` — будет вызван `MigrationManager.applyMigrations()` (N-1 → N).
4. **Проверить результат:**
   - В `schema_version` появилась запись с `version = N`.
   - Новые таблицы/поля/индексы присутствуют и доступны.
   - Существующие данные не повреждены (выборочная проверка записей в ключевых таблицах).
5. При ошибке — исправить миграцию в `N.sqm`, восстановить копию БД из бэкапа и повторить шаги 2–4.

Такой прогон обязателен при любом изменении схемы перед мержем и деплоем.

## Troubleshooting

### Проблема: Миграция не применяется

**Решение:**
- Проверьте, что файл миграции находится в правильной папке
- Проверьте, что миграция названа правильно (N.sqm)
- Проверьте логи для ошибок

### Проблема: Ошибка при применении миграции

**Решение:**
- Проверьте синтаксис SQL в миграции
- Убедитесь, что миграция идемпотентна
- Проверьте логи для детальной информации об ошибке

### Проблема: Версия схемы не обновляется

**Решение:**
- Проверьте, что миграция вставляет запись в `schema_version`
- Проверьте логи для ошибок при вставке

## Best Practices

1. **Всегда тестируйте миграции** на тестовых данных перед применением в production
2. **Создавайте backup** перед применением миграций в production (опционально, через BackupManager)
3. **Документируйте изменения** в комментариях миграции
4. **Используйте транзакции** для атомарности миграций (SQLDelight делает это автоматически)
5. **Не удаляйте старые миграции** - они могут понадобиться для восстановления

## Единая точка входа (все платформы)

**Миграция 1→2 и последующие применяются на всех платформах через один путь:**

- Инициализация БД выполняется только через `createDatabase(driver)` / `createDatabaseSync(driver)` из `shared/data/local/DatabaseFactory.kt` (commonMain).
- Android, iOS, Desktop и Server получают драйвер из `DatabaseFactory.createDriver()` (actual-реализации), затем вызывают `createDatabaseSync` или `createDatabase` — миграции и валидация выполняются в общем коде.

**Гарантии:**

1. **Миграции 1→2, 2→3** — вызываются в `MigrationManager.applyMigrations()` (по цепочке от текущей версии до `CURRENT_SCHEMA_VERSION`).
2. **После применения миграций** в `createDatabase()` всегда вызывается `MigrationManager.validateMigration(database, targetVersion)` для проверки версии и таблиц.

Добавление новых платформ должно использовать тот же сценарий: фабрика драйвера + `createDatabase`/`createDatabaseSync`, без обхода MigrationManager.
