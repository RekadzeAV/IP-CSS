# Правила формирования описаний обратной связи (Issues / отчёты)

**Версия:** 1.0  
**Дата:** 2026-03-01

Документ задаёт единые правила оформления описаний для пяти типов обратной связи: ошибки реализации, баги интерфейса, нарекания на дизайн, производительность/стабильность, идеи и пожелания.

---

## 1. Ошибки реализации

**Когда использовать:** некорректное поведение логики, API, интеграций, данных; падения, исключения, неверный результат вычислений.

### Обязательные поля

| Поле | Правило |
|------|--------|
| **Краткое название** | Одна фраза: что сломалось и при каких условиях (например: «Ошибка при сохранении камеры без RTSP URL»). |
| **Описание проблемы** | Что именно происходит (симптом), без интерпретации причины. |
| **Шаги воспроизведения** | Нумерованный список действий от «чистого» состояния до появления ошибки. |
| **Ожидаемое поведение** | Как должно работать по спецификации/документации. |
| **Фактическое поведение** | Что происходит на самом деле (сообщение об ошибке, код ответа, пустой результат и т.д.). |

### Рекомендуемые поля

- **Окружение:** ОС, версия приложения/сервера, версия зависимостей (если релевантно).
- **Логи/стек:** фрагменты логов, stack trace, код ответа API (без секретов и персональных данных).
- **Конфигурация:** приложить фрагменты конфига (без паролей и ключей).
- **Частота:** «всегда» / «иногда» / «при первом запуске» и т.п.

### Пример формулировки

- **Плохо:** «Не работает сохранение камеры.»
- **Хорошо:** «При нажатии «Сохранить» на форме добавления камеры без заполненного RTSP URL запрос уходит с пустым полем, сервер возвращает 400, в UI показывается общее сообщение «Ошибка», без деталей.»

### Связь с проектом

- По возможности указать компонент/модуль (например: `server/api`, `core/network`, `shared`).
- Если есть — ссылка на документацию или спецификацию, с которой расходится поведение.

## 2. Глюки и баги интерфейса

**Когда использовать:** некорректное отображение, зависания UI, неверная реакция на действия пользователя, визуальные артефакты, проблемы доступности.

### Обязательные поля

| Поле | Правило |
|------|--------|
| **Краткое название** | Экраны/компонент + суть (например: «Список камер не обновляется после добавления новой»). |
| **Описание** | Что видит пользователь: где именно (экран, вкладка, кнопка), что нажал/ввёл, что произошло. |
| **Шаги воспроизведения** | Пошагово: от открытия приложения/страницы до появления бага. |
| **Ожидаемое vs фактическое** | Что должно произойти в UI vs что произошло. |

### Рекомендуемые поля

- **Скриншоты/видео:** особенно для «миганий», неправильного layout, обрезанного текста.
- **Окружение:** платформа (Desktop x86/ARM, Android, веб), разрешение экрана, масштаб/DPI, браузер (если веб).
- **Частота:** всегда / только при определённых данных / после N действий.

### Пример формулировки

- **Плохо:** «Кнопка глючит.»
- **Хорошо:** «На экране «Камеры» после добавления камеры список не обновляется; новая камера появляется только после перезагрузки страницы. Кнопка «Обновить» не помогает.»

### Уточнения

- Указывать: сенсор/мышь/клавиатура, если баг воспроизводится только одним способом ввода.
- Для веб: указать, воспроизводится ли в другом браузере.

## 3. Нарекания на дизайн

**Когда использовать:** неудобство использования, непонятные элементы, визуальная перегруженность, несоответствие ожиданиям по оформлению (без поломки функциональности).

### Обязательные поля

| Поле | Правило |
|------|--------|
| **Краткое название** | Область интерфейса + суть претензии (например: «Слишком мелкий шрифт в таблице событий»). |
| **Что не устраивает** | Конкретный элемент или сценарий: что именно и где (экран, блок, компонент). |
| **Контекст использования** | Кто и зачем пользуется (роль, задача), чтобы было понятно, почему это мешает. |

### Рекомендуемые поля

- **Предложение по изменению:** как бы вы хотели видеть (размер, расположение, текст, порядок действий). Без жёсткого «как сделать в коде».
- **Скриншот/макет:** текущее состояние и при возможности — желаемый вариант (скрин с пометками или ссылка на макет).
- **Приоритет для вас:** низкий / средний / высокий (по желанию).

### Пример формулировки

- **Плохо:** «Дизайн некрасивый.»
- **Хорошо:** «На экране «События» в таблице столбец «Описание» обрезается одной строкой при длинном тексте; нет возможности быстро прочитать суть без перехода в детали. Предложение: показывать 2–3 строки с многоточием или тултип по наведению на ячейку.»

### Важно

- Отделять «не работает» (баг) от «неудобно/не нравится» (дизайн). Для багов использовать разделы 1 или 2.

## 4. Производительность и стабильность

**Когда использовать:** тормоза, долгая загрузка, высокое потребление ресурсов, вылеты, перезапуски, деградация со временем.

### Обязательные поля

| Поле | Правило |
|------|--------|
| **Краткое название** | Компонент/сценарий + тип проблемы (например: «Долгая загрузка списка записей при 500+ элементах»). |
| **Симптом** | Что именно наблюдается: время отклика, процент CPU/RAM, сообщение о падении, частота. |
| **Условия** | Нагрузка (число камер, записей, пользователей), объём данных, длительность работы до появления проблемы. |
| **Ожидания** | Приемлемое для вас время/поведение или референс (например: «раньше открывалось за 2 секунды»). |

### Рекомендуемые поля

- **Метрики:** время ответа (сек), использование CPU/RAM (%), размер логов/БД.
- **Окружение:** ОС, железо (RAM, CPU), версия приложения, режим (debug/release).
- **Логи:** фрагменты до/во время проблемы (без секретов).
- **Воспроизводимость:** всегда / под нагрузкой / после N часов работы.

### Пример формулировки

- **Плохо:** «Всё тормозит.»
- **Хорошо:** «Экран «Записи» при 600+ записях в БД открывается 12–15 секунд; при 100 записях — около 2 секунд. Ожидание: открытие не более 3–4 секунд при любом количестве записей или пагинация по умолчанию.»

### Уточнения

- Для падений/крашей: приложить stack trace, мини-дамп или шаги до падения.
- Для «со временем всё замедляется»: описать, через сколько и какие действия выполнялись.

## 5. Идеи, предложения и пожелания

**Когда использовать:** новая функция, улучшение процесса, изменение поведения по умолчанию, интеграции, без привязки к конкретному багу.

### Обязательные поля

| Поле | Правило |
|------|--------|
| **Краткое название** | Формулировка как цель/функция (например: «Экспорт событий в CSV по выбранному периоду»). |
| **Суть предложения** | Что вы хотите получить: сценарий использования или результат. |
| **Зачем это нужно** | Какую задачу или боль это закрывает (для приоритизации). |

### Рекомендуемые поля

- **Предлагаемое решение:** вариант реализации (кратко: «кнопка на экране событий + выбор дат + формат CSV»).
- **Альтернативы:** варианты, которые вы считаете приемлемыми.
- **Приоритет:** по желанию: nice-to-have / важно / критично.

### Пример формулировки

- **Плохо:** «Сделайте экспорт.»
- **Хорошо:** «Предложение: на экране «События» добавить экспорт выбранных событий (или за период) в CSV (время, камера, тип, описание). Нужно для отчётов для руководства без ручного копирования из интерфейса.»

### Связь с проектом

- Указать метку `enhancement` при создании Issue.
- Проверить, нет ли уже открытого предложения в Issues; при наличии — добавить аргументы в существующее.

---

## Общие правила для всех типов

1. **Один вопрос — один отчёт:** не объединять несколько не связанных проблем в один Issue.
2. **Без конфиденциальных данных:** пароли, токены, реальные IP/имена в примерах заменить на плейсхолдеры.
3. **Язык:** по умолчанию — русский; технические термины можно оставлять на английском.
4. **Ссылки:** при наличии — ссылка на документацию, другой Issue или PR.
5. **Метки:** использовать принятые в проекте метки (bug, enhancement, performance, design и т.д.) для быстрой фильтрации.

---

## Краткая шпаргалка по типам

| Тип | Фокус описания |
|-----|----------------|
| Ошибка реализации | Что сломалось, шаги, ожидаемое/фактическое, логи, окружение. |
| Баг интерфейса | Где в UI, что нажали, что увидели, шаги, скрин/видео, платформа. |
| Дизайн | Что не устраивает, где, контекст использования, предложение по изменению. |
| Производительность/стабильность | Симптом (время/ресурсы/падения), условия, метрики, ожидания. |
| Идеи и пожелания | Суть, зачем нужно, предлагаемое решение, приоритет. |
