# Поэтапный план реализации

**Версия:** 1.0  
**Дата:** 2026-03-01  
**Цель:** Завершение MVP с приоритизацией по критичности и зависимостям.

---

## Сводка по фазам

| Фаза | Название | Срок | Приоритет | Статус |
|------|----------|------|-----------|--------|
| **0** | Подготовка | 1–2 дня | Обязательно | ✅ Выполнено |
| **1** | ONVIF Event Service | 2–3 недели | Критический | ⚠️ Почти готово (остаётся 1.4.3) |
| **2** | Безопасность (pinning, HTTPS) | 1–2 недели | Критический | ✅ Выполнено |
| **3** | RTSP / FFmpeg | 1–2 недели | По требованию MVP | 🟡 Частично (остаётся 3.1.1) |
| **4** | CameraRepository — кэширование | 2–3 дня | Высокий | ✅ Выполнено |
| **5** | Миграции БД | 2–3 недели | Высокий, не блокер | ✅ Выполнено |

*Детальный статус задач — в [MVP_PHASED_IMPLEMENTATION_PLAN.md](MVP_PHASED_IMPLEMENTATION_PLAN.md).*

## Порядок выполнения и зависимости

```
                    ┌─────────────────────────────────────────────────────────┐
                    │  Фаза 0: Подготовка (1–2 дня)                           │
                    └───────────────────────────┬─────────────────────────────┘
                                                │
        ┌───────────────────────────────────────┼───────────────────────────────────────┐
        │                                       │                                       │
        ▼                                       ▼                                       ▼
┌───────────────┐                     ┌─────────────────┐                     ┌─────────────────┐

│ (2–3 нед)     │                     │ (1–2 нед)       │                     │ (2–3 дня)       │
└───────┬───────┘                     └─────────────────┘                     └─────────────────┘
        │
        │  после стабилизации сборки (опционально)
        ▼
┌───────────────┐                     ┌─────────────────┐
│ Фаза 3        │                     │ Фаза 5          │
│ RTSP / FFmpeg │                     │ Миграции БД     │

└───────────────┘                     └─────────────────┘
```

**Рекомендуемая последовательность:**

1. **Фаза 0** — первым делом (критерии MVP, ветки, тесты).
2. **Фаза 1** — основной фокус; закрыть оставшуюся задачу 1.4.3 (ручная проверка с ONVIF-камерой).
3. **Фаза 4** — можно в начале или параллельно с Фазой 1 (уже выполнена).
4. **Фаза 2** — параллельно или после Фазы 1 (уже выполнена).
5. **Фаза 3** — только если в MVP заложен «нативный» RTSP; иначе после MVP.
6. **Фаза 5** — по мере изменения схемы БД (уже выполнена).

## Фаза 0: Подготовка (1–2 дня)

**Цель:** Зафиксировать критерии готовности MVP и стабильное окружение.

| № | Задача | Результат |
|---|--------|-----------|
| 0.1 | Определить и записать в `docs/MVP_DEFINITION.md`: список обязательных фич MVP; что считается «нативным RTSP»; нужен ли принудительный HTTPS для MVP | Актуальное определение MVP |
| 0.2 | Проверить сборку и прогон тестов по `docs/TESTING_EXECUTION_GUIDE.md` (или аналог) | Подтверждённая инструкция по тестам |
| 0.3 | Завести ветку/метки для MVP (например `mvp-phase-1`) | Готовность к поэтапному релизу |

**Итог фазы:** Общий реестр задач и стабильная база для следующих фаз.

## Фаза 1: ONVIF Event Service — подписка и интеграция (2–3 недели)

**Цель:** Подписка на события ONVIF на сервере и клиентах; события в системе событий и в UI.

### Этап 1.1 — Сервер: подписка при старте (3–5 дней)

| № | Задача |
|---|--------|
| 1.1.1 | При старте API подписывать ONVIF-камеры на события; при add/update/delete камеры — подписка/переподписка/отписка |
| 1.1.2 | Входящие события передавать в `EventService.createEvent(...)` |
| 1.1.3 | Созданные события уходить в WebSocket |
| 1.1.4 | Конфиг: включение/выключение ONVIF подписок, таймауты, интервал PullPoint |

### Этап 1.2 — Клиенты (Desktop/Android): старт мониторинга (2–4 дня)

| № | Задача |
|---|--------|
| 1.2.1 | Desktop: при старте запускать мониторинг для всех камер |
| 1.2.2 | Android: при старте приложения инициализация мониторинга |
| 1.2.3 | Ошибки (нет сети, камера недоступна): не падать, логировать, переподписка при восстановлении |

### Этап 1.3 — Интеграция с системой событий и UI (3–5 дней)

| № | Задача |
|---|--------|
| 1.3.1 | Полный путь: ONVIF → EventService → WebSocket → веб/мобильный UI |
| 1.3.2 | Маппинг ONVIF-топиков в EventType/EventSeverity |
| 1.3.3 | Фильтры в UI (камера, тип, критичность) и обновление по WebSocket в реальном времени |
| 1.3.4 | Документировать сценарии: добавление камеры → авто-подписка; удаление → отписка; перезапуск → восстановление |

### Этап 1.4 — Тесты и стабилизация (3–5 дней)

| № | Задача |
|---|--------|
| 1.4.1 | Юнит-тесты маппинга ONVIF → доменное событие и подписка/отписка |
| 1.4.2 | Интеграционный тест: мок ONVIF → подписка → событие → WebSocket |
| 1.4.3 | Ручная проверка с реальной ONVIF-камерой (см. [MANUAL_ONVIF_CAMERA_VERIFICATION.md](MANUAL_ONVIF_CAMERA_VERIFICATION.md)) |

**Итог фазы:** События ONVIF доходят до UI; веб — в реальном времени по WebSocket.

## Фаза 2: Безопасность — certificate pinning и HTTPS (1–2 недели)

**Цель:** Pinning из конфига на всех платформах; при необходимости — принудительный HTTPS.

### Этап 2.1 — Финализация certificate pinning (3–5 дней)

| № | Задача |
|---|--------|
| 2.1.1 | Загрузка конфигурации pinning из файла/конфига во всех клиентах (Android, iOS, Desktop/JVM) |
| 2.1.2 | `enforcePinning = true` везде, где используется CertificatePinner |
| 2.1.3 | Проверить использование pinning в ApiClient/Ktor engine на всех платформах |
| 2.1.4 | Тесты: успешное соединение при валидном pin, отказ при неверном сертификате |

### Этап 2.2 — Принудительный HTTPS (2–4 дня)

| № | Задача |
|---|--------|
| 2.2.1 | Сервер: редирект HTTP → HTTPS (порт 80 → 443) и опция «только HTTPS» в конфиге |
| 2.2.2 | Клиенты: при «только HTTPS» не подключаться к http://; предупреждение или блокировка |
| 2.2.3 | Документация: включение HTTPS на сервере, генерация/добавление pins для продакшена |

**Итог фазы:** Безопасность подключений и опция «только HTTPS» при необходимости.

**Справка:** [HTTPS_AND_PINS_PRODUCTION_QUICKSTART.md](HTTPS_AND_PINS_PRODUCTION_QUICKSTART.md), [PRODUCTION_SETUP_CERTIFICATE_PINNING_HTTPS.md](PRODUCTION_SETUP_CERTIFICATE_PINNING_HTTPS.md).

## Фаза 3: RTSP — тестирование и доводка FFmpeg (1–2 недели)

**Цель:** Предсказуемая работа RTSP на JVM/Desktop (и при необходимости на Android) с тестами и обработкой ошибок.

*Критично только при требовании «нативного» RTSP в MVP.*

### Этап 3.1 — JVM/Desktop (1 неделя)

| № | Задача |
|---|--------|
| 3.1.1 | Прогон существующих тестов RTSP/декодера и фиксация падающих |
| 3.1.2 | Тесты на реальном RTSP-потоке (H.264/H.265): подключение, декодирование, остановка, реконнект |
| 3.1.3 | Обработка ошибок: таймауты, обрыв, неверный кодек — логирование, callback/Flow для UI |
| 3.1.4 | Стабилизация VideoDecoderImpl (рефлексия avcodec_open2, fallback на программный декодер) |

### Этап 3.2 — Android (опционально для MVP)

| № | Задача |
|---|--------|
| 3.2.1 | Проверить NativeRtspClient/ExoPlayer; при необходимости — доводка или переключение на ExoPlayer для RTSP |
| 3.2.2 | Документировать ограничения: кодеки/профили, нужен ли FFmpeg на устройстве |

**Итог фазы:** Стабильный RTSP на целевых платформах; ограничения задокументированы ([ANDROID_RTSP_MVP.md](ANDROID_RTSP_MVP.md)).

## Фаза 4: CameraRepositoryImpl — кэширование (2–3 дня)

**Цель:** Снижение нагрузки на сеть и ONVIF за счёт кэшей в V2.

### Этап 4.1 — DiscoveryCache и StatusCache в V2

| № | Задача |
|---|--------|
| 4.1.1 | Кэш для `discoverCameras()` в CameraRepositoryImplV2 (TTL 5–7 мин) |
| 4.1.2 | Кэш для `getCameraStatus(id)` (TTL 15–30 сек) |
| 4.1.3 | Инвалидация при add/update/delete камеры и при «обновить список обнаруженных» |
| 4.1.4 | Юнит-тесты: кэш в пределах TTL; после TTL — новый запрос к источнику |

### Этап 4.2 — Тесты и документация

| № | Задача |
|---|--------|
| 4.2.1 | Тесты для CameraRepositoryImplV2 (discovery и status через кэш) |
| 4.2.2 | Описать стратегию кэширования в docs (TTL, инвалидация) |

**Итог фазы:** В проде используется V2 с DiscoveryCache и StatusCache.

**Справка:** [CACHING_STRATEGY_CAMERA_REPOSITORY.md](CACHING_STRATEGY_CAMERA_REPOSITORY.md).

**Цель:** Предсказуемое версионирование схемы и процесс добавления новых миграций.

*Не блокирует выход MVP при стабильной текущей схеме.*

### Этап 5.1 — Текущее состояние

| № | Задача |
|---|--------|

### Этап 5.2 — Дальнейшие миграции

| 5.2.2 | Документировать в DATABASE_MIGRATIONS.md: как добавить миграцию, как проверить откат |

**Итог фазы:** Контроль версий схемы и регламент миграций.

## Критерии готовности MVP

- [ ] **Фаза 0** выполнена (MVP_DEFINITION согласован, тесты и ветки готовы).
- [ ] **ONVIF:** подписка при старте сервера и клиентов; события в UI; ручная проверка с реальной камерой (1.4.3) зафиксирована.
- [ ] **Безопасность:** pinning из конфига, принудительный HTTPS — по решению из Фазы 0.
- [ ] **RTSP** (если в scope): стабильное декодирование на JVM/Desktop; на Android — ExoPlayer; ограничения задокументированы.
- [ ] **CameraRepository V2:** кэши discovery и status, инвалидация, тесты.
- [ ] **Миграции БД:** процесс версионирования и добавления миграций описан и проверен.
- [ ] **Документация:** развёртывание, безопасность, тесты — актуальны.
